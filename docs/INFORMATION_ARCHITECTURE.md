# Svach AI HQ — Information Architecture

Scope of this document: the full navigation shell, plus a detailed page-by-page
breakdown of everything shipping in **Phase 1** (Dashboard/OOA, Sales, CRM). Delivery,
Marketing, Finance, and Support appear in the nav as locked placeholders in Phase 1 and
get their own detailed breakdown in this document once each phase begins (see
`ROADMAP.md`).

---

## 1. Global Navigation (Sidebar)

```
🏢 SVACH AI HQ
│
├── 🧭 Dashboard              [live — Phase 1]
│     OOA home: System Health + Business Insights
│
├── 📚 Knowledge              [live — Phase 1]
│     Global module — not a department, shared across every module & agent
│
├── 🎯 Sales                  [live — Phase 1]

│
├── 🚀 Delivery               [locked — "Coming in Phase 2"]
├── 📢 Marketing              [locked — "Coming in Phase 4"]
├── 💰 Finance                [locked — "Coming in Phase 3"]
├── 🎧 Support                [locked — "Coming in Phase 4"]
│
└── ⚙️ Settings                [live — Phase 1, minimal]
      Profile · Notification preferences
      (V1 is single-user/Owner-only — role & department fields exist in the
      schema for future multi-user support, but no team-management UI ships
      in V1; see DECISION_LOG.md §1, §3)
```

Locked modules are visible (not hidden) so the team always sees the full intended
system — clicking one shows an honest "this department goes live in Phase X" state,
never a fake preview or placeholder data.

**Persistent chrome** (present on every screen):
- Global search (leads, clients, knowledge documents — expands to more record types
  each phase)
- Notification bell (OOA alerts, approvals waiting on you)
- Account menu (profile, settings, sign out)

## 2. Dashboard (OOA Home)

The first screen after login. Two lenses, one page:

### 2.1 System Health (lens 1)
- Connected systems status strip (Supabase, n8n, any live integrations) — green/amber/red
- Recent workflow runs (from n8n): succeeded / failed / retried, with timestamps
- Failure/retry alerts, if any — link to the relevant n8n execution

### 2.2 Business Insights & Action Queue (lens 2)
- Card list of OOA recommendations, e.g. *"3 leads have gone cold — send a follow-up?"*
  — created by OOA (running on Hermes, `DECISION_LOG.md` §10), not generated by HQ
- Each card: **Approve** (executes directly if the action is fully specified, or
  notifies Hermes to delegate if it isn't — see `AI_ARCHITECTURE.md`'s two-branch
  approve-to-execute flow; either way, logs the action) / **Dismiss** (logs the
  dismissal — Hermes sees dismissal history via the API boundary and avoids repeating
  itself)
- Empty state when no recommendations exist yet: plain "No action needed right now,"
  never a fabricated suggestion to fill space

### 2.3 Agent Activity
Recent specialist-agent executions and their outcomes — a light, derived feed (built
from `audit_logs` and delegation-result data, no dedicated table) rather than a full
new module. Answers "what did the agents just do and how did it go" without requiring
a separate agent-status screen in Phase 1.

### 2.4 At-a-glance stats
- Open pipeline value / lead count by stage (from Sales)
- Clients flagged for follow-up (from Nexus)
- (Later phases add: active projects, revenue this month, open tickets)

## 3. Knowledge Module

Not a department — a shared, database-backed reference layer every module and every AI
agent can draw on (see `DECISION_LOG.md` §4). Content is authored in markdown but
stored as real records (Postgres), not flat files, specifically so it can carry version
history and be queried at runtime.

### 3.1 Knowledge List — Search & browse
Full-text search plus category/tag filters (e.g. "Sales Playbooks," "Pricing," "SOPs").
No semantic/embedding search in Phase 1 — deferred until there's enough content for
keyword search to fall short.

### 3.2 Document Detail
- Markdown content, rendered
- Category/tags
- Optional file attachments (Supabase Storage — e.g. a source PDF)
- Version history (one of only four entities with full version history — see
  `DECISION_LOG.md` §6)
- Edit-in-place for the Owner

### 3.3 New Document
Manual creation in Phase 1 — AI-assisted document generation (e.g. auto-drafting an SOP
from a completed workflow) is a later-phase enhancement, not V1.

### 3.4 Cross-module surfacing
In Phase 1, Knowledge is reached by navigating to it directly. Later phases can surface
relevant documents contextually inside other modules (e.g. a "Related Knowledge" panel
on a Lead or Client detail page) — not required for the module to be useful on day one.

## 4. Sales Module

### 4.1 Pipeline (default view) — Kanban board
Columns = pipeline stages, matching the named agents from the original workflow sketch:

| Stage | Corresponds to |
|---|---|
| Lead | Lead Hunter / Lead Research |
| Contacted | Email Outreach |
| Discovery Booked | Discovery Call |
| Proposal Sent | Proposal |
| Verbal Commit | said yes, contract not signed yet — no original named-agent counterpart |
| Won | Contract (signed) → becomes a Nexus client record |
| Lost | closed out, structured reason required (`DECISION_LOG.md` §12) |

Each card: lead name/practice, stage, last activity date, owner. Drag between columns
to change stage (writes an activity-log entry).

### 4.2 Lead List — Table view
Sortable/filterable alternative to the board (by stage, owner, last activity, source).

### 4.3 Lead Detail page
- Profile fields: practice name, contact, specialty (dental, med spa, etc. — matches
  svach.in's specialty list), source, stage
- Activity timeline: calls, emails, notes, stage changes
- **AI-assist panel**: draft an outreach email, summarize a discovery call from notes,
  suggest next action — human reviews/edits/sends, AI never sends directly in Phase 1
- Manual "Mark as Won" action → creates the linked Nexus client record automatically

### 4.4 New Lead form
Manual entry (Phase 1 has no autonomous Lead Hunter agent yet — that's a later-phase
promotion per `ROADMAP.md`).

## 5. Nexus (CRM) Module

Product-facing name for the CRM department is **Nexus** — see `DECISION_LOG.md` §3
addendum. Functionally, it's still client relationship management.

### 5.1 Client List — Table view
All active clients, with a health-flag column (rule-based in Phase 1: e.g. "no contact
in 14 days" = amber flag).

### 5.2 Client Detail page
- Profile: practice info, specialty, engagement start date, key contacts
- Onboarding checklist: 4-step strict sequential gate (Welcome sent → Contact
  confirmed → Billing collected → Kickoff scheduled), plus a pre-completed "Contract
  executed" entry — `DECISION_LOG.md` §12, full mechanics in `DATABASE_SCHEMA.md`
- Follow-up reminders: scheduled and past, with snooze/complete actions
- Activity timeline: shared with Sales history if the client originated as a lead
- **AI-assist panel**: draft a follow-up message, summarize recent activity

### 5.3 Follow-up Queue
Cross-client view of everything due or overdue — the Nexus equivalent of the Sales
pipeline board, surfaced separately since "who needs a follow-up today" is a daily
question, not a per-record one.
